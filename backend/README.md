# Quit Companion — Backend Services

For the completed Android/backend workflows, runtime setup and remaining
external release criteria, see [the completion record](../docs/ANDROID_COMPLETION.md).

FastAPI services for real (non-test) phone OTP delivery through the WhatsApp
Business Platform (Meta Cloud API) and AI-generated Health-Bot responses.

## Setup

```
python -m venv .venv
.venv/Scripts/activate   # .venv/bin/activate on macOS/Linux
pip install -r requirements.txt
cp .env.example .env     # then fill in real values — never commit .env
```

## Application structure

Feature packages keep their HTTP router alongside the service it exposes:

- `app/otp/` — phone OTP routes, OTP lifecycle, and storage
- `app/healthbot/` — Health-Bot route and intent service
- `app/relapse/` — relapse route, prediction service, and model loading
- `app/notifications/` — notification routes and delivery service
- `app/account_deletion/` — account deletion route and service
- `app/whatsapp/` — WhatsApp delivery providers used by phone authentication

`app/main.py` composes the feature routers into the FastAPI application.

## Required configuration (`.env`)

| Variable | Required for | Notes |
|---|---|---|
| `WHATSAPP_ACCESS_TOKEN` | sending real OTP messages | Meta system-user/app access token |
| `WHATSAPP_PHONE_NUMBER_ID` | sending real OTP messages | from Meta Business Manager |
| `WHATSAPP_BUSINESS_ACCOUNT_ID` | not read by current code | reserved, only needed if a future endpoint manages templates via the API |
| `WHATSAPP_API_VERSION` | — | defaults to `v20.0` |
| `WHATSAPP_OTP_TEMPLATE_NAME` | sending real OTP messages | must be an **approved authentication-category template** in Meta Business Manager |
| `FIREBASE_SERVICE_ACCOUNT_JSON` | verify-otp (minting sign-in tokens) | path to a service account key file — Firebase Console > Project Settings > Service Accounts > Generate new private key |

Without these set, `/auth/phone/send-otp` and `/auth/phone/verify-otp` return
a clear "not configured" failure (502/500) rather than silently pretending
to work — see `app/whatsapp/meta_client.py` and `app/firebase_identity.py`.

## AI-generated Health-Bot responses

Set `GEMINI_API_KEY` in the backend environment (or an uncommitted local
`.env`) to enable Gemini responses. The key is used only by the backend;
never place it in Flutter configuration or send it from a mobile client.
`GEMINI_MODEL` defaults to `gemini-3.5-flash-lite`.

The backend checks emergency phrases locally before making a Gemini request.
For other questions it returns a concise, contextual response generated by
Gemini, rather than mapping a topic label to a canned answer. The model is
instructed to stay within nicotine cessation and general recovery, avoid
diagnoses and medication instructions, and flag urgent situations. Missing
configuration, network errors, and invalid responses fall back to the local
rule-based knowledge base. These replies are labeled as general guidance
with AI unavailable; logs never include the API key or user query.
Health-Bot messages are sent to Google Gemini and are also saved in the user's
conversation history; the mobile app discloses both in its disclaimer.

## FCM notification sender

The mobile app registers opt-in device tokens in each user's private
`nicotineUsers/{uid}/fcmTokens` subcollection. The backend exposes
`POST /notifications/send/{notification_type}` for a trusted scheduler. The
route accepts only the fixed notification types `daily_checkin`,
`habit_reminder`, and `recovery_motivation`. The server selects the copy and
target token category. It never accepts caller-authored notification text.

Event notifications are separate and user-targeted:
`POST /notifications/events/badge_earned` and
`POST /notifications/events/restart_plan` require a verified Firebase ID token.
They send only to that user's opted-in device tokens. The app invokes them when
a new badge is awarded and when a relapse/restart plan is saved.

Configure `FIREBASE_SERVICE_ACCOUNT_JSON` in the backend deployment's secret
manager and deploy `mobile/firestore.rules` before token registration. FCM
credentials and Firebase Cloud Messaging/APNs platform setup are external
requirements. `FCM_SCHEDULER_TOKEN` and Cloud Scheduler are needed only if
daily/habit/recovery notifications are intentionally sent remotely; the app
currently schedules these locally using the device's timezone and selected
frequency, so scheduling the same categories remotely would cause duplicates.
Never send the scheduler secret or Admin credentials to the Flutter app.

## Account deletion

`DELETE /account` requires a verified Firebase ID token. Using the Admin SDK,
the service recursively deletes the user's `nicotineUsers/{uid}` document tree,
their authored `communityPosts` and nested threads, and their likes/replies on
other posts, then deletes the Firebase Auth user. Configure
`FIREBASE_SERVICE_ACCOUNT_JSON` in the backend deployment's secret manager.
The endpoint fails closed when Admin configuration is missing or deletion
fails; the client should sign out only after a successful response.

## Run

```
uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

`--host 0.0.0.0` is required for a physical device on the same network to
reach it — point the Flutter app at `http://<your-machine-LAN-IP>:8000` via
`--dart-define=OTP_BACKEND_BASE_URL=...` (see `../mobile/lib/core/config/otp_backend_config.dart`).

## Test

```
pytest -v
```

Tests never call the real WhatsApp API or Firebase Admin SDK — see
`app/whatsapp/fake_client.py` and `app/fake_firebase_identity.py`, wired in
via `tests/conftest.py`.
